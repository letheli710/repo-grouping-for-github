## 优先修复的实际问题

**P1，隐私：同一浏览器配置中的不同 GitHub 账号共用分组，可能暴露上一账号的私有仓库名。** `extension/content.js:14` 使用固定键 `ghg:v1`，`extension/content.js:136` 读取的登录名只用于隐藏自身 owner 前缀，没有参与存储隔离。测试先保存 Alice 的“私密客户项目”和 `alice/private-client-project`，再加载登录名为 Bob 的首页，结果仍然显示 Alice 的分组和私有仓库链接。这里暴露的是分组名、仓库名和归类关系，并没有授予 Bob 阅读私有仓库内容的权限；共享浏览器或工作、个人账号切换时仍然属于实际隐私问题。建议按从 GitHub 当前页面读取的账号标识隔离分组，不要求扩展登录或 OAuth，并设计旧版全局数据的明确归属迁移。

**P2，数据完整性：快速修改设置会丢失其中一项。** `extension/popup.js:26` 每次更新都独立执行“读完整对象、合并一个字段、写回完整对象”，没有对更新排序。测试在同一个事件循环中先把样式切换为 `band`，再勾选显示原生列表，最终存储为 `style: card, showNative: true`，前一项样式变更被覆盖。`extension/content.js:209` 也把整个分组对象写回同一键，多个页面并发修改分组存在同类的最后写入覆盖风险；本次直接复现的是设置面板的两项更新，并未把多标签竞争当作已实测结论。建议先拆分设置与分组的存储边界，并为设置更新串行处理；多个标签的分组修改还需要按操作合并或可靠的冲突检测，仅在每个页面各加一个队列并不能解决跨页面竞争。

**P2，数据完整性：内容脚本保存失败时，界面仍然表现为已经成功。** `extension/content.js:209` 只把保存错误输出到控制台，随后立即渲染新的本地状态，没有可见错误、回滚或重试。测试在扩展真实的隔离环境中，让这一页的存储写入拒绝，再新建分组，界面显示 3 个分组，实际存储仍只有 2 个，也没有可见错误提示。用户刷新后会失去看似已经完成的整理；相邻的启动逻辑 `extension/content.js:715` 也把读取失败当成空数据，后续编辑可能覆盖仍然存在的旧分组，这一点来自源码分析。建议区分“没有数据”和“读取失败”，并在写入失败时保留待保存修改、显示可重试状态，或恢复上一次成功保存的界面。

**P2，窗口与缩放：菜单没有视口边界处理，会被裁掉。** `extension/content.js:356` 根据按钮位置一次性定位菜单，`extension/content.js:668` 使用绝对定位，没有向上展开、菜单最大高度或自身滚动约束。先打开设置菜单，再把视口高度从 900 改成 180，菜单底部仍停在 228；在普通 100% 缩放、1024×600 视口中打开最后一项仓库的菜单，菜单从 y=576 延伸到 y=711，同样超出可视区域。后一个场景说明问题并不限于极端矮窗口；依靠滚动整个侧边栏可能还能找到选项，但菜单没有在打开或调整窗口后保证可见。建议对菜单做可用空间计算，必要时向上展开，限制高度并允许菜单内部滚动，同时在视口或锚点位置变化后重新计算。

**P2，页面生命周期：挂载点消失后没有清理旧界面，与现有降级承诺不符。** `extension/content.js:187` 找不到原生导航时直接返回，没有调用 `unmount()`。测试挂载成功后移除导航节点，等待观察器运行，旧的 `#ghg-root` 和 `ghg-hide-native` 类都仍然存在；这证明“找不到挂载点就自动恢复”的承诺没有完整落实，但不意味着本次观察到了线上 GitHub 侧边栏变空。建议在挂载点缺失、失效或不可用时明确卸载旧界面、清理菜单和拖拽状态，并恢复原生显示；随后找到有效挂载点再重挂载。

## 已复现机制、但依赖线上条件的问题

**P2，列表完整性：只展开一次并不能保证拿到所有仓库。** `extension/content.js:189` 的 `expandedOnce` 在点击一次 “Show more” 后就阻止后续展开，并且不会随挂载点重建而重置。测试构造 25 个仓库、首屏 10 个、每次再加载 10 个的侧边栏，结果只展示 20 个，原生列表和剩余的 “Show more” 按钮已经被隐藏，用户无法从分组列表继续展开。这个结果证明扩展不能处理需要多次展开的列表，并不证明 GitHub 当前线上一定采用这种分页方式；首次加载失败、返回首页或列表重建后需要重新展开，也有相同的机制风险。建议根据列表是否还有更多内容和加载是否完成来决定继续展开或提供用户可见的加载入口，同时限制重试和操作频率。

**P3，导航兼容性：只改 URL、没有 DOM 变化时不会重新判断页面。** `extension/content.js:700` 只监听 DOM 子节点变化，没有额外监听导航事件。测试使用 `history.pushState` 从首页切换到仓库路径且不修改 DOM，旧的分组界面仍然存在；加入 DOM 变化后就正常卸载。真实 GitHub 软导航通常伴随 DOM 更新，本次相应场景已通过，因此这里记录为需要覆盖的条件风险。建议优先使用 GitHub 已有的导航完成事件配合 `popstate` 等机制，在不扩大页面访问范围的前提下保持状态一致。

另外，当前仓库来源仅是首页的 Top repositories 列表，相关入口位于 `extension/content.js:145`。即使完整展开该列表，也不能据此承诺覆盖账号下所有仓库；不在列表中且尚未归过组的仓库，当前版本没有补充入口。这个范围限制与“查找全部仓库”的产品期望需要区分。

## 权限、联网与攻击入口

`manifest.json:6` 的 API 权限数组确实只有 `storage`，但 `manifest.json:16` 的 `content_scripts.matches` 同样授予在整个 `https://github.com/*` 注入的能力。当前代码在首页判断之后才读取侧边栏仓库，在其他 GitHub 路径仍会初始化样式节点和观察器，所以“只在首页显示分组”准确，“没有任何页面读取或修改权限”不准确。Chrome 官方说明，内容脚本可以读取和修改页面 DOM，JavaScript 的隔离环境不会把 DOM 限定为某一个侧边栏；权限说明见 [Declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions) 和 [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)。现有宽匹配有支持从仓库页软导航返回首页的用途，不能简单改成首页匹配而不同时处理这个场景。

“零网络请求”需要收紧措辞。产品代码里没有主动使用 `fetch`、XHR、WebSocket 或 beacon，但 `extension/content.js:291` 会创建远程头像图片，`extension/content.js:192` 会自动点击 GitHub 自己的加载按钮；前者能触发资源请求，后者是否产生请求取决于 GitHub 自己的实现。测试对头像返回禁止缓存的本地响应后，20 个原生头像和 20 个扩展头像共触发 40 个图片请求，证明扩展确实会创建新的远程资源加载；真实浏览器缓存命中时不一定增加网络往返。这些地址是 `avatars.githubusercontent.com`，本次没有发现向开发者服务器发送分组或私有仓库名称的代码，因此应把“存在头像请求”和“存在数据外传”分开描述。

`manifest.json:12` 的 `connect-src 'none'` 配置在 `extension_pages` 下，不能被当作内容脚本绝对无法联网的证明。Chrome 官方将这一策略的适用范围描述为扩展页面和 worker，包括 popup；内容脚本发起请求又有其自身的页面来源及同源限制，参见 [Manifest CSP](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy) 和 [Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)。脚本中的测试探针从真实扩展隔离环境请求同源的 `/__audit_network_probe`，成功取得本地拦截器返回的 HTTP 200 响应，证明该配置没有禁止这次请求；这不是在产品中发现了隐藏的 fetch。建议把当前承诺改为“不要求额外登录，不索取 token，不向开发者服务器上传分组或仓库数据；分组本地保存，可能复用 GitHub 的头像与页面加载”，如果确实要承诺严格不新增网络请求，就需要移除远程头像加载和自动加载操作并相应调整功能。

当前 XSS 防护的方向是合理的。分组名和仓库名使用 `textContent`，仓库链接、分组样式和颜色有白名单，源码没有 `innerHTML`、动态求值、远程脚本、外部消息入口或后台转发请求。测试把 `<img src=x onerror=alert(1)>` 放进分组名，把脚本 URL 和恶意 CSS 标记放进存储，结果分组名按文字显示，其余危险值被过滤，没有出现脚本执行或页面错误。Shadow DOM 的主要价值是隔离样式，当前 `mode: open` 仍允许页面脚本读取已经渲染出的分组信息；因此它不提供对 GitHub 页面自身的保密边界，也不应被宣传为凭据或权限隔离机制。

还需要保留对未来发布版本的信任边界：拥有 github.com 页面注入能力后，恶意更新不一定需要新增权限，就可以扩大 DOM 读取或页面操作的范围。Chrome 的权限升级保护针对的是新加入且会触发警告的权限，不能保证所有行为变化都会再次征求用户同意，参见 [Permission warning guidelines](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)。当前源码没有发现这种恶意行为，不过设计稿中提到的网络调用 CI 检查、发布校验和产物证明，在本目录中尚无对应实现。公开源码、可核对的发布包和持续的安全检查，才是支持长期信任的可验证措施。

## 关于封号、风控和浏览器提示

基于当前实现，没有看到自动 star、follow、提交表单、修改仓库、批量调用 API、绕过访问控制或高频抓取行为；主要动作是本地分组、读取当前侧边栏和一次自动展开。因此，对由这些已知行为导致账号封禁的风险，我的判断是较低，这属于基于代码行为的推断，不是 GitHub 的认可或零风险保证。GitHub 的 [Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies) 明确限制过量批量自动化、虚假互动、未授权访问等行为，并保留采取处置措施的权利；没有为这一扩展提供安全豁免。此次没有对真实账号运行压力测试，也没有声称能触发或验证 GitHub 的非公开风控逻辑。

浏览器安装时关于 github.com 数据读取和修改的提示，应当如实解释为页面整理功能所需的网站访问能力，不能用“只申请 storage”暗示用户不会看到网站访问提示。针对当前原型，建议先修复账号数据隔离、保存可靠性和菜单边界，再处理挂载与分页条件，并同步修正安全说明。这样可以继续保持不要求额外登录、不索取 token 的核心体验，同时把已经观察到的风险落到具体实现上。
